# 테스트 속도 개선

테스트가 느린 이유와 줄인 방법, 해 보고 채택하지 않은 것을 적는다. 측정은 2026-11-03~05, Windows, Docker Desktop에서 했다.

시간은 성격이 다른 두 가지로 나뉜다.

- **고정 비용**: 테스트를 한 번 실행할 때 한 번만 드는 시간. 테스트가 1개든 100개든 같다.
- **테스트당 비용**: 테스트마다 드는 시간. 테스트 수만큼 곱해진다. 대표적으로 회원 가입·로그인의 BCrypt 해시와 `@AfterEach`의 cleanUp이다.

## 고정 비용

테스트 클래스 하나를 실행하면 다음 구간을 순서대로 지난다.

| 구간 | 개선 전 | 개선 후 | 개선 |
|---|---|---|---|
| Gradle과 JVM 시작 | 약 5초 | 약 1초 | 1. IntelliJ로 실행 |
| 스프링 기동 (컨테이너 기동 포함) | 약 35초 | 약 25초 | 3. tmpfs |

- 스프링 기동은 로그의 `Started ... in N seconds` 값이다. IntelliJ에서 tmpfs를 끈 상태와 켠 상태를 3번씩 쟀고 중간값이다(끔 35.1초: 35.1, 37.3, 33.6 / 켬 25.2초: 25.2, 24.9, 25.2).
- 컨테이너는 `static` 블록에서 뜨는데 이 블록이 스프링 컨텍스트를 만드는 중에 실행되므로, 컨테이너 기동 시간이 스프링 기동 시간에 포함된다. 두 값을 더하면 안 된다.
- 컨테이너만 보면 개선 후 MySQL 약 7.6~8.0초, Kafka 약 3.6초, Redis 약 0.7초다. 3개는 병렬로 뜨므로 대기 시간은 가장 느린 MySQL이 정한다.
- tmpfs를 켜면 흔들림도 줄었다. 끈 상태는 33.6~37.3초로 3.7초 흔들렸고 켠 상태는 24.9~25.2초로 0.3초만 흔들렸다.

### 1. Gradle 대신 IntelliJ로 실행

- 테스트 실행 방식을 Gradle에서 IntelliJ로 바꿨다. JVM 시작부터 스프링 기동 시작까지가 약 5초에서 약 1초로 줄었다.
- 전체를 한 번에 확인하는 `./gradlew test`는 그대로 쓴다. CI가 생기면 그쪽이 기준이다.

### 2. 컨테이너를 JVM 하나에서 한 번만 띄우고 공유

- 컨테이너 3개를 `static` 필드로 두고 `static` 블록에서 한 번만 기동한다. 테스트 클래스마다 새로 띄우지 않는다.
- 격리는 컨테이너를 새로 만드는 대신 `@AfterEach`에서 데이터를 비우는 것으로 한다(아래 테스트당 비용).
- 컨테이너를 실행 사이에도 살려 두는 재사용(`withReuse`)은 쓰지 않았다. 이유는 ADR 0002.

### 3. MySQL을 tmpfs에 올리고 바이너리 로그 끄기

```java
new MySQLContainer<>("mysql:8.0")
        .withTmpFs(Map.of("/var/lib/mysql", "rw"))
        .withCommand(..., "--skip-log-bin");
```

데이터 디렉터리를 메모리(tmpfs)에 둬서 디스크 쓰기와 `fsync`를 없앴다. 바이너리 로그는 테스트에 필요 없어 껐다.

| 설정 | MySQL 기동 |
|---|---|
| 기본 | 약 15.3초 |
| tmpfs | 약 9.0초 |
| tmpfs + `--skip-log-bin` | 약 7.8초 |

전체 테스트(`./gradlew cleanTest test`)는 이 설정으로 통과했다.

참고: tmpfs는 기동 시간뿐 아니라 테스트 실행 중의 DB 작업(insert, update, commit, `TRUNCATE`)도 빠르게 해서 전체 테스트 시간도 줄어든다. 이 효과는 기동과 따로 떼어 측정하지 않았다.

**주의: tmpfs 때문에 이 환경의 DB 속도는 운영과 다르다.**
- 쓰기에 디스크 지연이 없어서 insert, update, commit이 운영보다 빠르다. 그래서 이 테스트로 쓰기 속도나 처리량을 재면 안 된다.
- 성능 측정은 운영과 비슷한 MySQL 설정, 디스크, 데이터 규모를 갖춘 별도 환경에서 부하 도구로 한다.
- 동시성 정합성(재고가 음수가 되지 않는가, 중복 예약이 없는가)은 락과 트랜잭션 로직이라 디스크와 무관하게 유효하다. 다만 쓰기가 빨라서 경합이 덜 겹칠 수는 있다.

## 테스트당 비용

테스트마다 반복되는 비용이 두 가지 있다. 회원 가입·로그인의 비밀번호 해시와 `@AfterEach`의 DB 정리다.

### 4. 가입·로그인의 BCrypt 강도 낮추기

거의 모든 API 테스트가 회원 가입과 로그인을 거친다. 가입은 `encode`, 로그인은 `matches`를 한 번씩 부르는데, 운영의 `BCryptPasswordEncoder`는 기본 강도가 10이라 한 번에 약 54ms가 든다(회원 한 명 준비에 약 108ms). 테스트에서는 허용되는 최소 강도 4로 낮춘 인코더를 `@Primary`로 끼운다(`TestBeanConfig`, ADR 0009).

Spring 없이 `BCryptPasswordEncoder`의 `encode`와 `matches`를 워밍업 10회 뒤 50회 평균으로 쟀다(2026-11-05, 같은 PC).

| 강도 | `encode` (가입) | `matches` (로그인) | 회원 한 명 준비 |
|---|---|---|---|
| 4 (테스트) | 1.11ms | 0.99ms | 약 2.1ms |
| 5 | 1.81ms | 1.74ms | 약 3.6ms |
| 6 | 3.59ms | 3.51ms | 약 7.1ms |
| 7 | 7.27ms | 7.07ms | 약 14.3ms |
| 8 | 13.81ms | 13.66ms | 약 27.5ms |
| 9 | 27.08ms | 27.09ms | 약 54.2ms |
| 10 (운영 기본) | 53.93ms | 53.82ms | 약 107.8ms |

- 강도가 1 오를 때마다 시간이 거의 정확히 2배가 된다. 10에서 4로 낮추면 반복 횟수는 64분의 1이지만 고정 비용 때문에 실제로는 약 49배 빠르다.
- 회원을 만드는 테스트 하나당 약 106ms를 아낀다. 100개면 약 10.6초다(위 표로 계산한 값이다. 전체 테스트를 강도 10으로 돌려 잰 값은 아니다).
- 알고리즘은 운영과 같은 BCrypt로 두고 강도만 낮춘다. 테스트용 `FakePasswordEncoder`로 바꾸지 않은 이유는 ADR 0009에 있다. 요약하면 비밀번호를 해시 문자열 `equals`로 비교하는 버그나 해시(60자)가 DB 컬럼에 안 맞는 문제처럼 실제 BCrypt에서만 드러나는 버그를 통과시킬 수 있고, 강도 4면 해시가 이미 약 1ms라 대역으로 얻는 이득이 작다.
- 강도가 낮아 해시 시간 특성은 운영과 다르다. 성능이나 보안 강도를 확인하는 테스트에는 쓰지 않는다.

### 5. 데이터가 있는 테이블만 TRUNCATE

테스트마다 `@AfterEach`에서 `DatabaseCleanUp.truncateAllTables()`가 DB를 비운다. 이 호출이 테스트 개수만큼 반복된다. 테이블마다 `SELECT 1 ... LIMIT 1`로 행이 있는지 먼저 보고, 있는 테이블만 `TRUNCATE` 한다. `TRUNCATE`는 행이 1건이든 1000만 건이든 빠르고 PK 증가값도 초기화해서 쓰지만, 빈 테이블에도 비용이 든다. 그래서 빈 테이블은 `SELECT`로 확인하고 건너뛰는 쪽이 싼지를 쟀다.

엔티티 테이블 10개에서 `truncateAllTables()` 호출 1회를 30회 반복한 평균이다.

| 데이터가 있는 테이블 | 있는 것만 | 전부 |
|---|---|---|
| 0개 | 22.3ms | 72.1ms |
| 5개 | 55.4ms | 70.1ms |

테이블 1개당 비용은 위 측정에서 역산한 값이다.

| | 비용 |
|---|---|
| 빈 테이블 `TRUNCATE` | 약 6~7ms |
| `SELECT` 확인 | 약 2ms |

- 빈 테이블은 `SELECT`(2ms)만 하고 건너뛰므로 `TRUNCATE`(6~7ms)보다 싸다.
- 데이터가 있는 테이블은 `SELECT` 후 `TRUNCATE`도 해야 하므로 `SELECT` 비용이 추가로 든다.
- 그래도 이 방식을 택한 이유: 테이블은 앞으로 계속 늘어난다. 한 테스트는 보통 자기와 연결된 테이블만 사용한다. 그래서 대부분의 테이블이 빈 채로 남고, `SELECT` 확인이 이득이라고 판단했다.
- 예: 테이블 50개에서 한 테스트가 5개만 쓰면, 위 1개당 비용으로 계산한 값은 다음과 같다(계산한 추정값이고 측정하지 않았다).
  - 전부 `TRUNCATE`: 50 × 6.5ms ≈ 325ms
  - 있는 것만: 50 × 2ms + 5 × 6.5ms ≈ 130ms
- 한 테스트가 테이블 대부분을 쓰는 테스트가 늘어나면 `SELECT`가 낭비가 되므로 다시 측정한다.

## 해 보고 채택하지 않은 것

| 시도 | 결과 | 판단 |
|---|---|---|
| 컨테이너 재사용(`withReuse(true)`) | 컨테이너 기동 약 15초에서 1초, 전체 약 15초 단축 | 컨테이너가 남고 Kafka 상태가 실행 사이에 이월된다. 실험 기능이라 채택하지 않았다(ADR 0002) |
| `--innodb-flush-log-at-trx-commit=0` | tmpfs 위에서는 추가 이득 없음 | 이미 디스크에 쓰지 않아 의미가 없다 |
| 지연 초기화(`lazy-initialization`) | 약 3초 단축 | 빈 생성 오류를 실행 시점으로 미뤄 문제를 늦게 발견하게 한다. 이득이 작아 제외했다 |
| JVM·GC 옵션 | 차이 없음 | 제외 |
| Kafka 리스너 끄기 | 차이 없음 | 제외 |

## 남은 후보

- 스프링 기동 구간 단축: AppCDS(클래스 데이터 공유) 등. 가장 큰 구간이라 다음 후보이며, 측정이 필요하다.
- 테스트 수가 늘어 전체 실행이 길어지면 컨테이너 재사용을 다시 검토한다(ADR 0002).
