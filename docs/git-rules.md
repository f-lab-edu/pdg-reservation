# Git 규칙

이 프로젝트의 브랜치 전략과 커밋 규칙. 현업에서 가장 흔히 쓰이는 GitHub Flow를 따른다.
`미정`으로 표시한 항목은 아직 정하지 않았다.

## 1. 브랜치 전략 (GitHub Flow)

### 브랜치

- `main` 하나만 상시 유지한다. 항상 배포 가능한 상태를 유지하고 직접 커밋하지 않는다.
- 모든 작업은 `main`에서 작업 브랜치를 따서 하고, `main`으로 돌려보낸 뒤 브랜치를 삭제한다.
- `develop`, `release`, `hotfix` 브랜치는 두지 않는다. 긴급 수정도 일반 작업과 같은 흐름으로 처리한다.

### 작업 흐름

1. `main`에서 작업 브랜치를 딴다.
2. 브랜치에서 작업하고 자주 커밋한다.
3. 원격에 푸시하고 Pull Request를 연다.
4. 리뷰와 자동 테스트(CI)를 통과하면 `main`에 머지한다.
5. 작업 브랜치를 삭제한다.

```
main    ──●──────●──────●──────●──
           \    /        \    /
작업브랜치  ●──●          ●──●
```

### 브랜치 이름

형식: `type/설명` (소문자와 하이픈)

| 접두사 | 용도 | 예시 |
|---|---|---|
| `feat` | 기능 추가 | `feat/refund-fee` |
| `fix` | 버그 수정 | `fix/stock-negative` |
| `refactor` | 동작 변화 없는 구조 개선 | `refactor/payment-facade` |
| `test` | 테스트 추가·수정 | `test/reservation-characterization` |
| `docs` | 문서 | `docs/git-rules` |
| `chore` | 빌드 설정, 의존성, 기타 잡무 | `chore/upgrade-spring-boot` |
| `perf` | 성능 개선 | `perf/search-index` |

- 접두사는 그 작업의 주된 목적을 나타낸다. 한 브랜치 안에 다른 type의 커밋이 섞여도 된다.
- 브랜치 하나는 하루~이틀 분량으로 짧게 유지한다.
- 접두사는 커밋 type과 같은 목록을 쓴다.
- 브랜치 이름은 훅으로 검사하지 않는다.

### 미정

- PR을 쓸지, 혼자 작업이라 로컬에서 직접 머지할지
- 머지 방식 (merge commit / squash / rebase)
- 이슈 번호를 브랜치 이름에 넣을지

## 2. 커밋 규칙 (Conventional Commits)

### 형식

```
<type>(<scope>): <요약>

<본문 (선택)>
```

- `scope`는 선택이다. 쓰면 도메인 이름을 쓴다. 예: `feat(payment): 환불 수수료 계산 추가`
- 요약은 한글로 쓴다.

### type

| type | 의미 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `chore` | 빌드 설정, 의존성, 기타 잡무 |
| `perf` | 성능 개선 |

### 규칙

- 한 커밋은 한 가지 의도만 담는다. "1. ~ 2. ~ 3. ~" 식으로 여러 가지를 묶지 않는다.
- 요약은 50자 이내로 쓰고 끝에 마침표를 찍지 않는다.
- 요약에는 무엇을 했는지, 본문에는 왜 했는지를 쓴다.
- 본문은 이유가 한 줄로 설명되지 않을 때만 빈 줄 하나를 띄우고 쓴다.
- `type`은 위 7개 중 하나여야 한다.

### 예시

| 구분 | 메시지 | 이유 |
|---|---|---|
| 나쁨 | `수정` | 무엇을 수정했는지 알 수 없음 |
| 나쁨 | `1. 리뷰 평점 카프카 이관 2. 알림 이관 3. 주석 제거` | 세 가지가 섞임 |
| 나쁨 | `feat 예약 추가` | `:`가 없어 형식 오류 |
| 좋음 | `feat: 리뷰 평점 갱신을 카프카로 이관` | 한 가지, type 있음 |
| 좋음 | `feat(payment): 환불 수수료 계산 추가` | scope 사용 |

```
fix: 재고 복구 시 음수 방지

만료 이벤트가 중복 도착하면 재고가 두 번 복구되어
총 재고를 넘는 문제가 있어 상한 검사를 추가함.
```

### 커밋 템플릿

루트의 `gitmessage.txt`가 커밋 템플릿이다. `git commit`을 `-m` 없이 실행하면 편집창에 규칙 안내가 `#` 주석으로 보인다. 주석은 커밋 메시지에 들어가지 않는다. 등록 방법은 [dev-guide.md](dev-guide.md)에 있다.

### 미정

- 머지 커밋 메시지 형식 (현재는 Git이 자동으로 만드는 `Merge `, `Revert `로 시작하는 메시지를 훅이 통과시킨다)
- 이슈 번호 사용 여부

## 3. Git Hook

`.githooks`에 두고 `core.hooksPath`로 연결한다. 연결 방법은 [dev-guide.md](dev-guide.md)에 있다.

| 훅 | 실행 시점 | 검사 |
|---|---|---|
| `commit-msg` | 메시지를 저장한 뒤 | 요약이 `type: 요약` 또는 `type(scope): 요약` 형식인지, 끝에 마침표가 없는지 |
| `pre-commit` | `git commit` 직후, 편집창이 열리기 전 | `.env` 파일 커밋 차단, `main` 직접 커밋 차단 |

### 검사하지 않는 것

- 요약 50자 제한 (셸이 한글을 바이트로 세어 정확히 셀 수 없다)
- 파일 안에 평문으로 적힌 비밀값 (`pre-commit`은 `.env` 파일 이름만 검사한다)
- 브랜치 이름
- `Merge `, `Revert `로 시작하는 자동 생성 메시지는 `commit-msg`가 통과시킨다.

### `pre-push` 훅을 두지 않는 이유

테스트는 Testcontainers로 MySQL·Redis·Kafka를 띄워서 오래 걸린다. 푸시마다 돌리면 `--no-verify`로 건너뛰는 습관이 생겨 훅이 무의미해진다. 전체 테스트는 GitHub Actions(CI)에서 돌린다.

### 한계

훅은 로컬에서만 동작하고 `git commit --no-verify`, `git push --no-verify`로 건너뛸 수 있다. 훅은 실수를 막는 안전망이고 강제 장치가 아니다. 강제는 GitHub의 브랜치 보호 규칙과 CI가 맡는다.
