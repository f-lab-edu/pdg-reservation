# 0016. 취소 진행 중 상태

- 상태: 채택
- 날짜: 2026-11-17

## 맥락
- 예약 취소는 PG 취소를 먼저 하고 DB를 나중에 바꿨다. PG 취소는 성공했는데 그 뒤 DB 단계가 실패하면 DB가 롤백되어, PG는 환불됐는데 예약과 결제는 `CONFIRMED`/`PAID`로 남는다. 결제 흐름과 달리 보상(되돌릴 방법)이 없고, 취소가 진행 중인지 끝났는지 구분할 상태도 없다.
- 가상 PG라서 결제 취소 결과를 조회하는 API가 없다. 그래서 멈춘 건을 PG에 물어 마무리하는 폴링은 할 수 없다.

## 결정
1. 예약과 결제에 `CANCELING`("취소 진행 중") 상태를 추가한다.
   - 예약: `CONFIRMED → CANCELING → CANCELED`, PG가 거절하면 `CANCELING → CONFIRMED`.
   - 결제: `PAID → CANCELING → CANCELED`, PG가 거절하면 `CANCELING → PAID`.
2. 취소 순서는 ① 한 트랜잭션에서 예약과 결제를 `CANCELING`으로 바꿔 커밋 ② PG 취소 호출(트랜잭션 밖) ③ 한 트랜잭션에서 결제 취소, 취소 이력, 예약 취소, 점유 해제를 확정한다.
   - ①이 실패하면 PG를 아직 부르지 않았으므로 아무 일도 일어나지 않는다.
   - ②에서 PG가 예외를 내면 한 트랜잭션으로 원래 상태로 되돌리고 오류를 그대로 올린다.
   - ③이 실패하면 `CANCELING`으로 남는다. 자동 복구는 하지 않고, 에러 로그로 수동 확인한다.
3. 취소 가능 여부는 지금처럼 예약이 `CONFIRMED`일 때만 통과한다. `CANCELING`인 예약을 다시 취소하면 기존 `PAYMENT_006`으로 거절된다. 점유한 밤은 `CANCELED`로 확정될 때 풀리고, `CANCELING` 동안은 그대로 둔다.
4. `READY`, `FAILED`, `PARTIAL_CANCELED`는 추가하지 않는다. 결제 흐름은 보상으로 안전하게 돌고 있고, 부분 환불은 R2-5(취소·환불 정책) 뒤에야 의미가 있다.

## 검토한 대안
- 순서를 그대로 두고 DB 실패를 무시: 돈과 상태가 어긋난다.
- DB를 먼저 확정하고 PG를 나중에 호출: PG 취소는 되돌릴 수 없어서, DB가 취소인데 PG가 거절하면 반대 방향으로 어긋난다.
- `CANCELING`으로 멈춘 건을 폴링으로 복구: PG 조회 API가 없어 지금은 못 한다. PG 조회나 멱등 재취소가 생기면 로드맵 R5-7에서 한다.

## 결과
- 멈춘 건은 `CANCELING`이라는 흔적이 남아 찾을 수 있다. 하지만 사람이 확인해야 한다.
- PG 예외를 모두 "거절"로 보고 원래 상태로 되돌린다. 타임아웃처럼 결과를 모르는 경우를 구분하지 않는다. 이전에도 DB가 롤백되어 같은 결과였으므로 후퇴는 아니고, 구분은 R5-7에서 한다.
- API에 새 상태 값이 나간다. 예약 검색의 상태에 `CANCELING`이 나타날 수 있다.
- 테이블과 컬럼은 바뀌지 않아 ERD는 그대로다(상태는 문자열 컬럼이고 스키마는 `ddl-auto: create`로 만든다).
