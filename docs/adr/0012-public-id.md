# 0012. 외부 식별자 public_id(UUID v4)와 내부 PK 유지

- 상태: 채택
- 날짜: 2026-11-05

## 맥락
- 지금은 내부 PK(`AUTO_INCREMENT` `BIGINT`)가 API 경로 변수와 응답, 캐시 키에 그대로 나간다.
- 내부 PK를 노출하면 값을 하나씩 바꿔 가며 추측할 수 있고(열거), 총 건수와 생성 순서가 드러난다.
- 소유자 검증(조회 조건에 `member_id`, 남의 리소스는 404)이 1차 방어이고, 외부 식별자는 추측을 어렵게 하는 추가 방어선이다.
- 로드맵의 설계 결정은 내부 PK와 외부 노출용 `public_id`를 분리하는 것까지 정했고, 이 문서에서 내부 PK 전략과 `public_id`의 형식·저장·적용 범위를 정한다.

## 결정
- **내부 PK는 `AUTO_INCREMENT`를 유지한다.** InnoDB는 PK 순서로 행을 저장해서 증가하는 값은 항상 끝에 붙고 페이지 분할이 적다. 모든 보조 인덱스 항목이 PK 값을 함께 저장하므로 PK가 작을수록(`BIGINT` 8바이트) 보조 인덱스가 작다. 단일 DB라 분산 생성도 필요 없다.
- **외부에 노출하는 식별자는 별도 컬럼 `public_id`로 두고 UUID v4(무작위)를 쓴다.** 생성 시각, 순서, 건수가 드러나지 않고 추측할 수 없다.
- 엔티티 필드는 `UUID` 타입이다. 변환기는 두지 않고 Hibernate의 기본 매핑에 맡긴다(MySQL에서는 `BINARY(16)`으로 알고 있고, 구현할 때 실제 컬럼 타입을 확인한다).
  ```java
  @Column(nullable = false, updatable = false, unique = true)
  @Builder.Default
  private UUID publicId = UUID.randomUUID();
  ```
  - 엔티티를 만들 때 애플리케이션이 값을 채운다. 저장 전에도 값이 있어서 응답이나 캐시 키를 만들 때 쓸 수 있다.
  - `@Builder.Default`가 없으면 빌더로 만들 때 초기값이 무시되어 `null`이 된다.
  - DB 기본값(`DEFAULT (UUID())`)은 쓰지 않는다. MySQL의 `UUID()`는 시간 기반(v1)이라 v4가 아니다.
- **적용 기준: id로 접근할 때 권한 검사가 필요한 비공개 리소스이면서 id가 API로 노출되는 엔티티에만 `public_id`를 붙인다.** 공개 정보나 노출하지 않는 엔티티에는 붙이지 않고, 공개 리소스가 열거로 문제가 되면(예: 유료 데이터 보호) 그때 확장한다.

  | 구분 | 엔티티 | 이유 | `public_id` |
  |---|---|---|---|
  | 비공개 (본인 것만 접근) | `Reservation`, `Payment` | 권한 검사가 한 번 빠지면 id 열거로 남의 데이터에 접근한다. 추가 방어선이 의미 있다 | **붙임** |
  | 비공개, 외부에 노출하지 않음 | `Member` | 키를 응답·경로로 내보내지 않고 JWT만 응답한다(JWT subject는 이메일). 노출 경로가 없다 | 붙이지 않음 |
  | 공개 정보 | `Accommodation`, `Room`, `Review` | 누구나 볼 수 있는 상품 정보라 id를 열거해도 새는 것이 업무 정보(건수, 증가 속도) 정도다. 크롤링은 rate limit으로 대응한다. 쇼핑몰의 상품 페이지도 숫자 id를 쓴다 | 붙이지 않음 |
  | 외부에 나가지 않음 | `AccommodationImage`, `RoomInventory`, `PaymentCancelHistory`, `EventLog` | 노출 경로가 없다 | 붙이지 않음 |
- 예약과 결제의 API 경로, 응답, 에러 메시지, 알림 링크에는 내부 PK가 아니라 `public_id`를 쓴다. 숙소·객실·리뷰는 지금처럼 숫자 id를 쓰므로 캐시 키와 Bloom Filter는 바뀌지 않는다. 컨트롤러가 받은 `public_id`로 조회하는 방법(리포지터리 `findByPublicId…`)은 엔티티마다 사이클을 돌면서 정한다.
- `public_id`는 소유자 검증을 대신하지 않는다. 기존 IDOR 방어(조회 조건에 `member_id`, 남의 리소스는 404)를 그대로 유지한다.
- 스키마 변경 수단(Flyway)이 아직 없으므로 개발·운영 프로필 모두 지금은 `ddl-auto: create`로 테이블을 새로 만든다(운영 DB에 지켜야 할 데이터가 없음을 확인했다). 개발 프로필의 `data.sql` 실행은 샘플 데이터의 예약·결제 INSERT(각 2건)에 `public_id`가 없어 삽입이 실패하므로 끈다. Flyway를 도입할 때(R3-5) 운영은 `validate`로 되돌리고, 샘플 데이터는 `public_id`를 채워서 다시 켠다.

## 검토한 대안
- 내부 PK를 UUID v4로: 무작위 삽입이 테이블 데이터(클러스터드 인덱스)에 일어나고 모든 보조 인덱스 항목에 16바이트가 붙어 전부 커진다.
- UUID v7, ULID, Snowflake(PK 또는 `public_id`): 시간 순서가 있어 삽입 성능이 좋지만 값 안에 생성 시각이 들어 있어 노출하면 시각이 드러난다. Snowflake는 ID 생성기도 필요하다.
- NanoID: 21글자로 짧고 URL 친화적이지만 UUID만큼 표준 지원(JPA 타입, DB 함수)이 넓지 않다. 이 프로젝트에서는 짧은 URL이 중요하지 않다.
- `CHAR(32)`(하이픈 제거) + 변환기: DB에서 읽기 쉽고 포스트맨 호출에 편하지만 변환기를 직접 만들어야 하고 인덱스가 `BINARY(16)`의 2배다. 포스트맨 호출은 API 응답의 문자열을 그대로 쓰면 되므로 필요하지 않다.
- `CHAR(36)`(`@JdbcTypeCode(SqlTypes.CHAR)`): 변환기는 필요 없지만 인덱스 항목이 36바이트다. DB를 직접 볼 일이 많아지면 어노테이션 하나로 바꿀 수 있다.
- Hashids처럼 PK를 가공한 값: 구현이 쉽지만 무작위가 아니라 소금 값이 새면 풀리고 보안 수단으로 약하다.
- 지금처럼 내부 PK를 그대로 노출: 열거와 건수 노출이 남는다.
- 공개 리소스(숙소, 객실, 리뷰)까지 전부 `public_id`를 붙이기: 외부 경로에서 내부 PK를 완전히 없애 일관되지만, 공개 정보라 열거의 피해가 작은 데 비해 변경 범위가 크다(숙소는 경로, 응답, 캐시 키, Bloom Filter, 리뷰·객실 API, 테스트까지 번진다). 엔티티마다 유니크 인덱스도 늘어난다. 필요해지면 확장한다.

## 결과
- `public_id` 유니크 인덱스가 엔티티마다 하나 늘고 무작위 삽입의 비용이 이 인덱스 하나에 생긴다. 페이지 분할로 인덱스가 커지고, 유니크 인덱스는 InnoDB 체인지 버퍼를 쓰지 못한다. 이 규모에서는 문제가 아니고, 규모가 커져 이 인덱스가 병목이 되면 시간 순서가 있는 값(UUID v7)으로 바꾸는 것을 검토한다(생성 시각이 드러나는 대가).
- 외부 조회는 `public_id` 인덱스 → PK → 행의 두 번 탐색이다.
- DB에서 직접 볼 때는 `BIN_TO_UUID()`와 `UUID_TO_BIN()`이 필요하다.
- 예약과 결제 API의 경로와 응답이 바뀌므로 외부 동작이 달라지는 변경이다. 엔티티마다 테스트를 먼저 고치고(실패 확인) 코드를 바꾸는 사이클로 진행하고, 매번 전체 테스트가 통과하는 상태를 유지한다. 예약과 결제는 결제 요청(`PaymentRequest.reservationId`), 취소 요청, 리뷰 작성(예약 id), 예약 검색 응답 등 서로를 참조하는 곳이 있어 함께 바뀐다.
- 숙소·객실·리뷰의 id, 캐시 키, Bloom Filter는 바뀌지 않는다.
- 개발·운영 프로필의 `create`는 서버를 켤 때마다 테이블을 지우고 새로 만든다. Flyway를 도입하기 전의 임시 상태다.
