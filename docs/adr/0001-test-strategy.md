# 0001. 테스트 전략

- 상태: 채택
- 날짜: 2026-11-01

## 맥락
- 기존 테스트는 `contextLoads` 하나뿐이다. 리팩토링(R3)과 동시성·결제 신뢰성 작업 전에 요구사항을 지키는 안전망이 필요하다.
- 참고 강의(Spring Boot TDD)는 API 통합 테스트를 중심에 두고 테스트 대역(Mock) 사용을 줄이라고 한다.

## 결정
- **API 통합 테스트 중심**으로 간다. 실제 서버를 띄우고 HTTP 요청·응답으로 요구사항을 검증한다.
- 서비스·리포지터리 단위로 층을 나눠 피라미드를 쌓지 않는다.
- **Mock 같은 테스트 대역은 최소로 쓴다.** 실제 구성요소를 제어할 수 없을 때(예: 외부 PG)에만 Fake를 고려한다.
- DTO는 따로 테스트하지 않고 API 테스트로 검증한다.
- 엔티티 단위 테스트는 엔티티에 로직(생성 규칙, 상태 전이)이 생긴 뒤에 추가한다(로드맵 R3-6).
- 테스트는 `test` 프로필로 돌리고 `data.sql`은 실행하지 않는다(`spring.sql.init.mode: never`).

## 검토한 대안
- 단위·서비스·리포지터리 테스트 피라미드: Mock이 늘어 설계를 바꾸기 어려워지고, 운영 코드는 문제인데 테스트만 통과하는 경우가 생긴다.
- 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest`): 실제 연결을 검증하지 못하고 설정이 늘어난다.

## 결과
- 테스트마다 실제 DB·Redis·Kafka가 필요해서 Docker가 실행 중이어야 하고 단위 테스트보다 느리다.
- 요구사항 변경에 테스트가 덜 민감하다.
- 규칙의 세부는 `docs/test-guide.md`에 있다.
