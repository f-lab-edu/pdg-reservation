# 0005. 저장소 초기화 방식

- 상태: 채택
- 날짜: 2026-11-01

## 맥락
- 컨테이너를 테스트 전체가 공유하므로 테스트 사이에 데이터가 남으면 서로 영향을 준다.
- DB, Redis, Kafka는 성격이 달라서 같은 방식으로 지울 수 없다.

## 결정
- **호출**: 각 테스트 클래스의 `@AfterEach`에서 **그 테스트가 사용하는 저장소만** 초기화한다.
- **DB**: `DatabaseCleanUp.truncateAllTables()`. 엔티티의 `@Table` 이름을 모아 외래 키 검사를 끄고 전부 `TRUNCATE`한 뒤 다시 켠다. 검사 설정이 연결 단위라서 `@Transactional`로 같은 연결을 쓰게 한다.
- **Redis**: `RedisCleanUp.flushAll()`. `FLUSHALL`로 전체를 지우고, 블룸 필터 설정도 같이 지워지므로 `AccommodationBloomFilter.init()`으로 빈 필터를 다시 만든다. 로그인처럼 Redis를 쓰는 테스트에서 추가한다.
- **블룸 필터**: 숙소를 만드는 Fixture는 저장 후 `bloomFilter.add(id)`를 한다.
- **Kafka**: 비우지 않는다. 비동기 처리가 끝나는 흐름은 Awaitility로 결과를 기다린 뒤 테스트를 끝낸다.

## 검토한 대안
- `@BeforeEach`에서 초기화: 이전 테스트가 정리를 빠뜨린 상태로도 시작할 수 있지만, `@AfterEach`로 정했다.
- Redis 키 접두사별 삭제(블룸 필터 키 제외): 지울 키 이름을 전부 알아야 하고 Redisson 내부 키 이름에 기대게 된다.
- Kafka 토픽 삭제·재생성: 재시도 토픽과 컨슈머 그룹이 불안정하고 느리다.
- 테스트마다 컨테이너 재기동: 너무 느리다.

## 결과
- 정리를 호출하지 않는 클래스가 있으면 상태가 다음 클래스로 새어 나간다. 부담이 되면 JUnit 확장으로 자동 실행한다.
- 이전 테스트의 Kafka 소비가 늦게 DB를 건드릴 수 있다. 흔들리면 컨슈머 랙 대기 도우미를 추가한다.
- 결제 대기 키의 만료 리스너(`ReservationTimeoutListener`)는 설계를 바꿀 예정이라 지금은 다루지 않는다.
