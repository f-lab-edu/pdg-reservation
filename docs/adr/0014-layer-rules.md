# 0014. 계층별 배치 규칙 (임시)

- 상태: 임시 채택. ERD 수정(R2-1 사이클 3~5)이 끝난 뒤 아키텍처 개선(R2-2, R3-1)에서 확정하거나 대체한다.
- 날짜: 2026-11-16

## 맥락
- 로드맵의 계층·DDD 정리(R2-2, R3-1)를 뒤에 두면서, 그 사이에 쓰는 코드의 위치를 조각마다 즉석에서 정하게 되었다. 가격 계산 하나에도 정적 계산기, 서비스, 값 객체, 엔티티 메서드가 후보로 나오고 이름(`overrides`)과 타입(`Collection`/`List`)까지 매번 다시 논의했다.
- 기존 코드는 리포지터리가 Response를 만들고, 검증 규칙이 `ReservationValidator`에 따로 있고, 일부 엔티티만 로직을 갖는 식으로 섞여 있어 따라 할 기준이 모호하다.
- 전체 아키텍처(Facade 범위, 트랜잭션 경계, 애그리거트)는 R2-2와 R3-1에서 정한다. 이 문서는 그 전까지 **새로 쓰는 코드**가 따를 최소한의 임시 배치 규칙만 정한다.

## 결정

### 계층별로 두는 것
| 계층 | 두는 것 | 두지 않는 것 |
|---|---|---|
| 엔티티, 값 객체 | 도메인 규칙, 상태 전이, 자기 데이터로 하는 계산 | DB 조회, 스프링 의존 |
| 도메인 서비스 | 여러 애그리거트에 걸쳐 어느 한 엔티티에 둘 수 없는 규칙(드물다), 상태 없음 | 단순 가공, 데이터 조립 |
| 애플리케이션 서비스 | 읽기, 도메인 객체 호출, 저장, 트랜잭션, 이벤트 발행(조율) | 계산, 정책 판단 |
| 리포지터리 | 조회와 저장. 엔티티 또는 조회 전용 프로젝션을 돌려준다 | Response 생성, 도메인 계산 |
| 컨트롤러 | Request/Response 변환 | 규칙 |

### 세부 규칙
1. **규칙은 데이터를 가진 객체에 둔다.** 서비스 메서드에 계산이나 도메인 상태에 대한 `if`가 생기면 엔티티나 값 객체의 메서드로 옮긴다.
2. **엔티티는 연관 데이터를 직접 조회하지 않고 인자로 받는다.** 행이 많아질 수 있는 데이터(예: 날짜별 특별 요금, 점유 행)는 엔티티가 컬렉션으로 소유하지 않고 서비스가 조회해서 넘긴다.
3. **값 객체는 불변 `record`**이고 식별자가 없다. 계산 결과 같은 저장하지 않는 값도 값 객체다(`NightPrice`, `StayPrice`).
4. **새 개념이 정말 필요할 때만 새 클래스를 만든다.** 이미 있는 엔티티와 값 객체로 풀 수 있으면 중간 객체(`Rates`, `Info` 등)를 만들지 않는다.
5. **새로 만드는 리포지터리 메서드는 Response를 돌려주지 않는다.** 기존 `@QueryProjection` Response는 R3-1에서 정리한다. 집합 단위로 하는 판정(가용성 같은 `EXISTS`)은 쿼리에 두고, 도메인 계산(가격)은 쿼리에 넣지 않는다.
6. **트랜잭션은 애플리케이션 서비스가 소유한다.** 도메인 객체에는 `@Transactional`을 쓰지 않는다.
7. **명명:** 변환 팩토리는 `from`(단일 소스), `of`(여러 값). 자바 용어와 겹치는 이름(`override` 등)을 도메인 이름에 쓰지 않는다.
8. **컬렉션 인자:** 서비스는 `List`, 리포지터리는 `Collection`(`Set`도 받으므로).
9. **테스트:** 엔티티와 값 객체의 도메인 규칙은 단위 테스트로(테스트 가이드의 엔티티 단위 테스트 위치 규칙), 사용자 관점의 동작은 API 테스트로 확인한다.

### 적용 범위
- **새로 쓰는 코드**에만 적용한다(R2-1 사이클 3~5).
- 이미 쓴 코드는 이 규칙에 맞추지 않고 아키텍처 개선 단계(R2-2, R3-1)에서 한꺼번에 맞춘다. 맞춰야 할 사이클 2 코드는 로드맵 R3-1에 적어 둔다: 가격 계산을 `StayPriceCalculator`에서 `Room.calculateStayPrice(체크인, 체크아웃, 특별 요금들)`로 옮기고, `AvailableRoom`을 없애고, `RoomPriceService`의 조립 코드를 줄이고, 단위 테스트를 `RoomTest`로 옮긴다.
- 규칙과 어긋나는 기존 코드를 발견하면 로드맵 R3-1에 적어 둔다.

## 검토한 대안
- 규칙을 정하지 않고 사이클마다 즉석에서 정하기: 같은 논의가 반복되고 코드가 조각마다 달라진다.
- R2-2의 전체 아키텍처(애그리거트, Facade, 트랜잭션 경계)를 먼저 확정: 범위가 크고 ERD 수정(사이클 3~5)이 그만큼 늦어진다. 임시 규칙만 먼저 두고 전체는 이후 단계에서 정한다.
- 사이클 2 코드를 지금 규칙에 맞게 고치기: ERD 수정 뒤 아키텍처 개선에서 어차피 다시 손대므로 두 번 고치지 않기로 했다.
- 계산을 정적 계산기(도메인 서비스)로 두기: 단일 엔티티(`Room`)의 데이터로 풀리는 계산이라 엔티티 메서드가 더 맞다.

## 결과
- 사이클 3~5는 위치를 논의하지 않고 이 표를 따른다. 규칙을 바꿔야 하면 이 ADR을 고친다.
- 기존 코드와 새 코드의 스타일이 아키텍처 개선 전까지 섞여 있다.
- 임시 규칙이라 R2-2, R3-1에서 애그리거트와 계층 경계를 정할 때 일부가 바뀔 수 있다.
