# 0011. 평점 갱신과 캐시 무효화 방식 (리뷰)

- 상태: 채택
- 날짜: 2026-11-05

## 맥락
- 리뷰를 쓰거나 지우면 Kafka 소비자(`ReviewKafkaConsumer`)가 비동기로 숙소 평점(합계, 개수, 평균)을 갱신하고 캐시를 무효화한다.
- 관련 캐시는 둘이다.
  - 리뷰 목록 첫 페이지: 숙소당 조건 조합(최소 평점 × 정렬 × 페이지 크기)만큼 키가 생긴다.
  - 숙소 상세: 숙소당 키가 하나(`숙소 id`)이고 평점을 담는다.
- 숙소 상세는 소비자가 평점을 갱신한 뒤 키를 지워서 무효화했다(캐시 어사이드의 "갱신 뒤 삭제"). 이때 경쟁이 있다. 상세를 조회하는 요청이 DB에서 옛 평점을 읽은 뒤, 소비자가 평점을 갱신하고 키를 지우고 나서야 그 옛 값을 캐시에 넣으면, 지운 의미가 없어지고 옛 평점이 TTL 동안 남는다. 리뷰 테스트에서 평점 확인 호출이 이 경쟁에 걸려 "기대 4.0, 실제 0.0"으로 실패하면서 드러났다. 스파이로 순서를 강제한 테스트로 항상 재현된다.

## 결정
- 리뷰 목록 캐시는 버전 키 방식으로 무효화한다(원래 적용됨). 숙소별 버전 번호(`review:version:{숙소 id}`)를 캐시 키에 넣고, 소비자가 번호를 올리면 이후 조회는 새 키로 찾아 DB에서 새로 읽는다.
  - 이유: 키 조합이 방대해서 모두 찾아 지우기 어렵다(`KEYS`는 Redis를 멈추고, `SCAN`은 훑는 부하가 크고, 키 인덱스는 관리가 번거롭다). 번호만 올리면 지우는 작업이 없어 Redis 부하가 없고, 옛 키는 TTL로 사라진다.
- 숙소 상세 캐시도 같은 버전 키 방식으로 바꾼다. 갱신 뒤 삭제 경쟁을 구조적으로 피하기 위해서다. 늦게 들어온 옛 값이 이미 아무도 읽지 않는 옛 버전 키에 쌓인다. 버전 번호는 리뷰 목록과 같은 숙소별 버전을 쓴다(소비자가 평점을 갱신하면서 이미 올리는 번호다). 소비자는 더 이상 상세 캐시를 지우지 않는다.
- 숙소 평균 평점은 갱신된 합계와 개수로 계산한다. MySQL의 `UPDATE`는 `SET`을 왼쪽부터 적용하고 앞에서 바꾼 값을 뒤의 식에서 쓴다. 갱신 전 값으로 계산하는 식이면 두 번째 리뷰부터 평균이 어긋난다(4.0, 2.0이면 3.0이 아니라 2.7).

## 검토한 대안
- 갱신 뒤 키 삭제(원래의 숙소 상세): 단순하고 키가 하나일 때 흔한 방식이지만, 위 경쟁이 있다.
- 짧은 TTL로 옛 값이 남는 시간을 줄이기: 경쟁은 그대로 남고 남는 시간만 줄어든다.
- 지연 이중 삭제(갱신 직후와 잠시 뒤 두 번 삭제): 경쟁을 줄이지만 완전히 없애지 못하고, 지연 시간을 정해야 한다.
- 평점을 상세 캐시에서 분리(본문은 길게 캐시, 평점은 매번 DB 조회): 코드 변경이 크고 상세 요청마다 DB 조회가 늘어난다.
- 갱신과 조회를 같은 락으로 묶기: 캐시 쓰기(`@Cacheable`)가 락 밖에서 일어나서 구조를 바꿔야 한다.
- 리뷰 목록의 `KEYS + DEL`, `SCAN + DEL`, 키 인덱스: 위 이유로 쓰지 않았다.

## 결과
- 버전 키는 조회마다 버전을 읽는 Redis `GET`이 한 번 더 든다. 옛 버전 키는 TTL까지 남는다. 버전이 오르면 새 키는 비어 있어 첫 조회들이 DB를 읽는데, 락과 재확인(double-check)이 같은 DB 읽기가 몰리는 것을 줄인다.
- 갱신이 반영되는 시점은 소비자가 번호를 올린 뒤다(최종 일관성). 번호가 오르기 전에 시작한 요청은 옛 값을 한 번 받을 수 있지만 다른 요청에는 번지지 않는다.
- 버전 키 이름이 `review:version:`이라 숙소 상세도 이 이름을 쓰게 된다. 이름을 일반화하는 것은 Redis의 기존 값과 어긋나므로 리팩토링(R3)에서 한다.
- 이 결정을 지키는 테스트는 `accommodations/id/GET_specs`의 "평점이 갱신되는 도중에 끝난 조회가 옛 평점을 캐시에 남기지 않는다"다.
- 리뷰 삭제 이벤트가 생성 이벤트로 발행되던 문제(`REVIEW_DELETED`)는 별도로 수정했다.
