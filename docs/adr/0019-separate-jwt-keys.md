# 0019. 액세스 토큰과 리프레시 토큰의 서명 키를 분리한다

- 상태: 채택. 구현은 R3-4(보안 보강)에서 한다.
- 날짜: 2026-11-17

## 맥락

### 지금 구조
- 로그인과 재발급 때 액세스 토큰과 리프레시 토큰을 **같은 키 하나(`jwt.secret`)** 로 서명한다. 두 토큰을 구분하는 클레임도 없다.
- 리프레시 토큰은 HttpOnly 쿠키(`refreshToken`)로 내려가고, Redis에는 `RT:{이메일}` 키로 **계정당 한 개(가장 최근에 발급한 값)** 가 저장된다. 응답 본문의 `LoginResponse`에는 들어가지 않는다.
- 재발급(`/reissue`)은 쿠키의 토큰에서 이메일을 꺼내 Redis 슬롯과 값을 대조한다. 같으면 새 토큰 두 개를 발급하면서 슬롯을 덮어쓴다(Rotation). 다르면 슬롯을 지우고 거절한다(탈취 감지). 로그아웃은 슬롯을 지우고 요청에 실린 **액세스 토큰 문자열**을 블랙리스트에 올린다.
- API 인증 필터(`JwtAuthenticationFilter`)는 `Authorization: Bearer` 토큰의 서명, 만료, 블랙리스트만 확인한다.

### 문제: 리프레시 토큰이 액세스 토큰 자리에서 통과한다
두 토큰이 같은 키로 서명되고 종류 구분이 없어서, 서명과 만료만 보는 필터는 리프레시 토큰도 유효한 인증 토큰으로 받아들인다. 리프레시 토큰은 7일짜리라서 다음 세 가지 방어가 한꺼번에 우회된다.

1. **로그아웃이 안 먹는다.**
   - 로그아웃은 Redis 슬롯을 지우고 제시된 액세스 토큰 문자열을 블랙리스트에 올린다.
   - 훔친 리프레시 토큰 R을 `Bearer R`로 쓰면 필터는 Redis 슬롯을 보지 않고, R은 블랙리스트에 없다. 사용자가 로그아웃해도 R은 만료(최대 7일)까지 통과한다.
   - 정상 사용자의 클라이언트는 자기 액세스 토큰으로 로그아웃하므로 R이 블랙리스트에 오를 일이 없다.
2. **Rotation과 탈취 감지가 무력화된다.**
   - 탈취 감지는 옛 토큰이 `/reissue`에 도착해야 작동한다(슬롯의 최신 값과 달라서 슬롯을 지운다).
   - 공격자가 `/reissue`를 거치지 않고 R을 Bearer로 계속 쓰면 대조 경로가 한 번도 실행되지 않는다. 정상 사용자가 몇 번 재발급해도 R은 계속 통과하고, 감지 신호도 울리지 않는다.
3. **액세스 토큰을 짧게 잡은 의미가 사라진다.**
   - 액세스 토큰을 짧게(운영 30분) 두는 것은 탈취돼도 피해 기간을 줄이기 위해서다. 리프레시 토큰이 같은 자리에 통과하면 피해 기간이 리프레시 토큰의 수명인 7일이 된다.
   - 리프레시 토큰이 매 API 호출의 헤더로 오가서 로그와 프록시에 남을 기회도 는다. 원래는 HttpOnly 쿠키로 재발급 경로에만 가는 값이다.

### 리프레시 토큰이 유출되는 것 자체는 원래 위험하다
- 리프레시 토큰은 가진 사람이 액세스 토큰을 계속 새로 받을 수 있는 "로그인 자격"이다. 공격자가 `/reissue`로 체인을 이어가면 새 리프레시 토큰이 매번 7일씩 연장되어 유효 기간이 사실상 무제한이 된다.
- 이 경로에는 방어가 있다. 정상 사용자가 로그아웃하면 슬롯이 지워져 모든 리프레시 토큰이 대조에 실패하고, 정상 사용자의 옛 토큰이 `/reissue`에 오면 슬롯이 지워져 공격자의 최신 토큰도 같이 무효가 된다(계정 슬롯이 하나라서 공격자의 토큰을 따로 몰라도 된다).
- 문제는 Bearer 경로가 **그 방어를 전부 건너뛴다**는 점이다. 이 경로의 7일은 사용자가 로그아웃해도 닫을 수 없다.

## 결정
**액세스 토큰과 리프레시 토큰을 서로 다른 키로 서명한다.**

- 설정을 둘로 나눈다: `jwt.access-secret`, `jwt.refresh-secret`. 운영 프로필은 각각 환경변수(`JWT_ACCESS_SECRET_KEY`, `JWT_REFRESH_SECRET_KEY`)로 받는다.
- 액세스 토큰은 access 키로만, 리프레시 토큰은 refresh 키로만 서명하고 검증한다.
- API 인증 필터는 **access 키로만** 검증한다. 리프레시 토큰은 서명이 맞지 않아 인증 단계에서 거절된다.
- 재발급(`/reissue`)은 **refresh 키로만** 검증한다. 액세스 토큰을 내밀어도 거절된다.
- 서명 검증 단계에서 구조적으로 구분되므로, 토큰 종류를 확인하는 코드를 따로 쓰지 않아도 된다(검사를 빠뜨릴 수 없다).

### 이 결정으로 막히는 것
| 우회 | 결과 |
|---|---|
| 리프레시 토큰을 `Bearer`로 API 호출 | access 키로 검증이 실패해서 401. 로그아웃, Rotation 우회, 7일 열림이 모두 닫힌다 |
| 액세스 토큰을 `/reissue`에 제출 | refresh 키로 검증이 실패해서 거절 |

### 이 결정으로 막히지 않는 것
- 리프레시 토큰이 `/reissue`에서 유출 후 사용되는 위험 자체는 남는다. 그 경로의 방어(Rotation, 탈취 감지, 로그아웃 폐기)는 지금처럼 유지한다.
- 계정당 슬롯이 하나라서 한 계정의 다중 기기 로그인은 탈취로 오인되어 서로를 로그아웃시킨다. 지금은 그대로 둔다(다중 기기는 슬롯을 `RT:{이메일}:{세션 id}`처럼 나눠야 한다).
- 재발급이 계속되는 한 리프레시 토큰은 사실상 만료되지 않는다(절대 세션 상한이 없다).

## 검토한 대안

### A. 같은 키 + 토큰 종류 클레임(`type: access` / `refresh`)
- 가장 흔하고 가볍다. 시크릿이 하나라 설정이 단순하다.
- 단점: 종류를 확인하는 코드를 필터와 `/reissue` 모두에 빠뜨리지 않고 넣어야 한다. 검증 코드가 틀리면 구분이 사라진다(구조가 아니라 규칙에 의존).
- 같은 키가 유출되면 두 토큰을 모두 위조할 수 있다.

### B. 토큰마다 다른 키 (채택)
- 서명 검증이 곧 종류 구분이라서 구조적으로 안전하다.
- 키 유출의 영향이 분리된다. 한쪽 키가 유출돼도 다른 종류의 토큰은 위조할 수 없다.
- 두 키의 교체 주기를 다르게 가져갈 수 있다(액세스 키는 자주, 리프레시 키는 드물게).
- 단점: 시크릿이 둘이라 설정과 환경변수가 늘고, 교체할 때 둘을 따로 관리해야 한다. 이 프로젝트에서는 감수할 수 있는 비용이다.

### C. 리프레시 토큰을 JWT가 아닌 랜덤 문자열로 서버(Redis)에만 보관
- 서명 구분이 필요 없고 폐기가 쉽다.
- 단점: 현재 구조(JWT 리프레시와 쿠키)를 크게 바꿔야 한다. 변경이 커서 이번에는 하지 않는다.

## 결과
- 리프레시 토큰이 API에 통과하는 경로가 구조적으로 사라진다.
- 설정 키가 둘이 된다. 기존에 발급된 토큰은 새 키로 검증되지 않으므로 배포 직후 모두 다시 로그인해야 한다(개발 환경이라 문제없다).
- 테스트: 리프레시 토큰으로 보호 API를 호출하면 401이다(로그아웃 전후 모두), 액세스 토큰으로 `/reissue`를 호출하면 거절된다, 기존 인증 테스트는 그대로 통과한다.
- 개발 프로필(`application-dev.yml`)의 시크릿이 git에 평문으로 있는 문제는 이 결정과 별개로 남아 있다(로컬 개발용이라 우선순위를 낮췄다).

## Resource Server(OAuth2 라이브러리)로 전환할 때
- 로드맵 R3-3에서 직접 만든 `JwtAuthenticationFilter`를 Spring Security OAuth2 Resource Server로 바꿀 수 있다. 이 결정은 그대로 유지된다.
- Resource Server의 `JwtDecoder`는 **access 키 하나만** 쓰도록 설정한다(대칭키를 쓰는 `NimbusJwtDecoder.withSecretKey(...)`). 리프레시 토큰은 다른 키라서 이 디코더에서 자동으로 거절된다.
- 같은 키를 쓰는 방식(A)이었다면 디코더에 `type` 클레임을 검사하는 `OAuth2TokenValidator`를 따로 추가해야 했다. 키를 분리하면 이 검증 코드가 필요 없다.
- Resource Server는 액세스 토큰을 검증하는 부분만 맡는다. 로그인, 리프레시 토큰 발급과 `/reissue`(refresh 키로 직접 검증), Redis 슬롯 관리는 지금처럼 우리 코드가 맡는다.
