# 0007. 검증 방식

- 상태: 채택
- 날짜: 2026-11-01

## 맥락
- 요구사항을 검증하고 구현 세부에는 묶이지 않는 테스트가 목표다.
- 응답에 드러나지 않는 결과(암호화된 비밀번호 등)와 Redis·Kafka 같은 내부 상태를 어떻게 볼지 정해야 했다.

## 결정
- 검증은 기본적으로 **API 응답**으로 한다.
- 응답에 나오지 않는 결과(예: 암호화되어 저장된 비밀번호, 아웃박스 기록)만 DB를 직접 조회해서 확인한다.
- 캐시는 키 존재가 아니라 **동작**(오래된 값이 남지 않는다 등)으로 검증한다. 캐시·블룸 필터·분산 락처럼 성능 장치가 실제로 작동하는지는 소수의 테스트로 따로 확인한다.
- Kafka를 거치는 흐름은 발행 여부가 아니라 **최종 결과**를 Awaitility로 기다려 검증한다.
- 토큰은 형식(JWT 세 부분, 헤더 `alg`, `sub`)을 확인하고, 이후 인증 API 호출이 되는지로 검증한다.
- 테스트 본문은 `// Arrange`, `// Act`, `// Assert`로 구분한다. 메서드 이름은 한글 문장으로 쓰고 `@DisplayName`은 쓰지 않는다.

## 검토한 대안
- 리포지터리로 모든 저장 결과를 직접 조회: 스키마가 바뀌면 테스트가 같이 깨진다.
- Redis 키와 Kafka 토픽 내용을 직접 읽어 확인: 구현 세부(키 이름, 직렬화)에 묶인다.

## 결과
- DB 직접 조회는 응답에서 볼 수 없는 결과에만 쓰는 예외라, 쓸 때마다 이유가 있어야 한다.
- 비동기 흐름 테스트는 대기 시간이 필요하다. `@RetryableTopic` 재시도(1초부터 2배씩, 최대 5회)를 감안해 최대 대기 시간을 넉넉히 잡는다.
