# 0018. 결제 요청의 멱등성 키

- 상태: 채택
- 날짜: 2026-11-17

## 맥락
- 결제 중복은 예약 id 기준 분산 락과 예약 상태 검사(`PAYMENT_003`)로 막고 있다. 락은 요청이 끝날 때까지 유지되고(`leaseTime = -1`), 끝난 뒤의 같은 요청은 상태 검사가 거절한다.
- 남는 틈은 락이 사라지는 인프라 장애(Redis 재시작, 페일오버)뿐이다. 그때는 두 요청이 PG 승인까지 가고, 뒤의 DB 단계에서 낙관적 락(`Reservation.@Version`)과 `payment.reservation_id` 유니크가 한쪽을 실패시킨 뒤 보상 취소로 수습한다. PG 승인 전에 중복을 거르는 장치는 없었다.
- 검토한 것: 예약을 `PAYING`으로 선점하는 방식(규칙을 엔티티에 두고 `@Version`으로 비교 후 갱신)과 멱등성 키 테이블. 선점은 상태 하나, 되돌리기, 만료 타이머 재설정, 멈춘 `PAYING` 처리가 따라와서 더 복잡하다.

## 결정
1. `POST /api/v1/payments`는 `Idempotency-Key` 헤더(1~64자)를 필수로 받는다. 없거나 길이가 맞지 않으면 400 `PAYMENT_012`다. 클라이언트가 결제 시도마다 새 키를 만든다.
2. `PaymentFacade.pay`의 **맨 앞**(PG 호출 전)에서 `idempotency_key` 테이블에 키를 `INSERT IGNORE`로 선점한다.
   - 이미 쓴 키면 409 `PAYMENT_011`로 거절하고 PG를 부르지 않는다.
   - 선점에 성공하면 지금의 결제 로직(락, 검증, PG 승인, 확정, 보상 취소)을 그대로 실행한다.
   - `PaymentFacade.pay`는 `NOT_SUPPORTED`라서 선점은 `IdempotencyKeyService.claim`의 자체 트랜잭션으로 바로 커밋된다. 이후 단계가 실패해 롤백돼도 키 행은 남는다.
3. **실패해도 키를 지우지 않는다.** PG 거절, 확정 실패, 서버 다운 어느 경우에도 클라이언트는 새 키로 다시 시도한다. 키에는 상태도 응답도 없고 "이미 썼다"는 기록뿐이라서, 멈춘 `IN_PROGRESS` 같은 상태를 복구할 필요가 없다.
4. 같은 키가 다시 오면 첫 응답을 되돌려 주지 않고 거절만 한다. 첫 요청이 성공했는데 응답을 못 받은 클라이언트는 예약 상태를 조회해서 확인한다.
5. 테이블 `idempotency_key`: `key_value`(유니크, 64자)와 생성 시각. 코드는 `common/idempotency`에 둔다.

## 이번에 하지 않는 것
- 오래된 키 정리 배치(쌓여도 부담이 작다), 키와 요청 본문 해시 대조, 응답 재생, 취소 API의 멱등성 키.

## 검토한 대안
- 예약 `PAYING` 선점(조건부 갱신 또는 `@Version`): 키가 다른 중복까지 서버 쪽에서 막지만 상태 전이와 복구 처리가 늘어난다. 보류하고 R5(만료 폴링)에서 필요하면 다시 본다.
- 키 상태(`IN_PROGRESS`/`COMPLETED`)와 응답 저장: 응답을 재생할 수 있지만 서버가 중간에 죽으면 `IN_PROGRESS`로 멈춘다.
- `event_log` 재사용: 목적이 다른 데이터가 섞여서 별도 테이블을 둔다.

## 결과
- 같은 키의 재전송은 PG 호출 전에 거절된다. 락이 사라지는 장애에서도 같은 키의 중복 승인은 막힌다.
- **클라이언트가 재시도마다 새 키를 만들면 이 방어는 작동하지 않는다.** 그 경우는 지금처럼 락, 상태 검사, `@Version`, `payment.reservation_id` 유니크, 보상 취소가 막는다.
- API 계약이 바뀐다. 결제 호출은 `Idempotency-Key` 헤더가 필수다.
- 실패 후 재시도에는 항상 새 키가 필요하다.
