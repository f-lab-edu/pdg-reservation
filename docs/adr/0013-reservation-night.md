# 0013. 객실 점유를 예약의 날짜별 행(reservation_night)으로 바꾼다

- 상태: 채택
- 날짜: 2026-11-16

## 맥락
- 지금은 객실의 날짜별 재고 행(`ROOM_INVENTORY`)을 미리 채워 두고, 예약이 들어오면 `is_stocked`를 `false`로 바꿔 점유를 표시한다. 취소와 만료 때는 `restoreStock`이 날짜 범위로 행을 찾아 `true`로 되돌린다.
- 이 구조의 문제는 세 가지다.
  - 날짜가 지날 때마다 새 날짜 행을 채우고 지난 행을 정리하는 배치가 있어야 한다. 배치가 멈추면 그 날짜는 예약할 수 없다. 행의 존재가 "그날 판매한다"를 뜻하기 때문이다.
  - 예약과 재고 행이 FK로 이어져 있지 않아서, 어느 예약이 어느 행을 막았는지 DB는 모른다. 복구는 객실과 날짜 범위로 행을 찾아 되돌리는 코드에 의존한다.
  - 이중 예약 방지가 DB 제약이 아니라 객실 단위 분산 락(`LOCK:room:{roomId}`)과 재고 행의 `@Version`에 달려 있다. 락을 빼 보면 한 건만 성공하지만 나머지 응답이 409가 아니라 500이 된다.
- `RoomInventory`를 읽는 곳은 예약 경로만이 아니다. 숙소 검색과 객실 목록의 가용성 판정과 가격 계산(`RoomExpressions`, `AccommodationRepositoryImpl`, `RoomRepositoryImpl`)도 재고 행에 의존한다.
- 객실(`Room`)은 호실 하나(`is_stocked`가 불리언)이고 한 객실 종류에 여러 호실이 있는 모델이 아니다. 그래서 날짜별 수량 카운터는 필요 없다. `SKIP LOCKED`는 "바꿔 쓸 수 있는 항목 중 아무거나 하나"를 고를 때 쓰는 도구라서, 특정 객실의 특정 날짜 집합이 필요한 이 문제에는 맞지 않는다.

## 결정

### 1. 판매 가능한 날은 차단일로만 표현한다
- 예약 가능 기간의 상한(예: 1년)은 두지 않는다. 기본 검증(체크인이 오늘 이후, 체크아웃이 체크인보다 뒤)은 요청 DTO가 그대로 맡는다.
- 판매하지 않는 날(공사, 휴업)은 `room_blocked_date(room_id, blocked_date)`에 행으로 둔다. `(room_id, blocked_date)`가 유니크다. 예약 전에 검사하고, 숙소 검색과 객실 목록에서도 제외한다.
- 차단일을 점유 행(`reservation_night`)에 섞지 않는다. 이미 예약된 날은 유니크 때문에 차단 행을 넣을 수 없어서, 예약을 먼저 취소한 뒤 차단을 넣어야 하고 그 사이에 다른 고객이 다시 예약할 수 있다. 별도 테이블이면 순서를 바꿀 수 있다.
- 운영 순서는 블록을 먼저 넣고(커밋되는 순간부터 새 예약이 막힌다), 그다음 차단일과 겹치는 기존 예약을 조회하고(`reservation_night` JOIN `room_blocked_date`, 반복 실행할 수 있는 조회), 영향받는 고객만 운영자 취소와 알림으로 처리한다. 블록이 커밋되기 직전에 검사를 통과한 예약이 이후에 점유를 끝내는 좁은 틈은 이 충돌 조회로 나중에라도 발견한다.
- 계절 운영처럼 긴 구간을 닫아야 하면 필요해질 때 객실에 판매 기간 컬럼을 추가한다. 지금은 두지 않는다.

### 2. 날짜별 가격은 특별 요금 테이블로 두고 계산은 자바 한 곳에서 한다
- `room_special_price(room_id, price_date, price)`는 기본 요금과 다른 날짜에만 행을 둔다. `(room_id, price_date)`가 유니크이고 가격은 0보다 커야 한다. 행이 없는 날은 `room.base_price`다(지금 재고 행의 "가격이 NULL이면 기본 요금"과 같은 의미).
- 날짜별 가격과 합계 계산은 `Room.calculateStayPrice(체크인, 체크아웃, 특별 요금들)` 엔티티 메서드 한 곳에서 한다(ADR 0014의 배치 규칙). 입력은 객실의 기본 요금, 기간, 그 기간의 특별 요금 행이다. 특별 요금은 행이 많아질 수 있어 객실이 소유하지 않고 서비스가 조회해서 넘긴다. 특별 요금 행은 `[체크인, 체크아웃)` 범위만 조회한다(체크아웃 날은 밤이 아니다).
- 예약 검증, 객실 목록, 숙소 검색이 모두 이 계산기를 쓴다. 목록과 검색은 이미 페이지를 먼저 조회한 뒤 가격을 구하는 2단계라서 객실들의 특별 요금 행을 한 번에 가져와 객실별로 계산한다. 가격으로 정렬하거나 거르는 기능이 없어서 자바 계산이 문제가 되지 않는다.
- 소수 처리(반올림)를 한 곳에서 정한다. 지금 검색 쪽은 `castToNum(Long.class)`로 소수를 버리는데, 목록 가격과 예약 검증 가격이 어긋나지 않게 하나로 맞춘다.
- 예약할 때 날짜별 가격(할인 전)을 `reservation_night.price`에 스냅샷한다. 이후 요금표를 바꿔도 이미 한 예약의 금액은 변하지 않는다. 등급 할인은 지금처럼 합계에 적용하고 `reservation.total_price`는 할인 후 값이라서, 박별 합계와 다를 수 있다.

### 3. 가용성은 점유와 차단이 하나도 겹치지 않는 것이다
- 객실이 기간 `[체크인, 체크아웃)`에 예약 가능하다는 것은 그 객실의 `reservation_night`와 `room_blocked_date`에 기간과 겹치는 행이 하나도 없다는 뜻이다(`NOT EXISTS` 두 개). 숙소 검색은 인원 조건을 만족하는 가용 객실이 하나라도 있으면 숙소가 나온다.
- 지금의 "기간의 모든 날짜에 행이 있고 모두 비어 있는가(행 개수 = 박수)"는 쓰지 않는다. 재고 행이 아예 없는 객실도 예약 가능해진다(1번 결정과 같은 이야기다).
- `(room_id, stay_date)`, `(room_id, blocked_date)` 유니크 인덱스를 범위 탐색에 쓴다. 넓은 검색의 실제 속도는 R3-7(인덱스 재설계)에서 `EXPLAIN`으로 확인한다.

### 4. 기간 검증
- 요청 DTO 검증(체크인 오늘 이후, 체크아웃이 체크인보다 뒤)은 그대로 둔다.
- `inventories.size() != nights` 검사는 없어진다. 대신 기간에 차단일이 끼어 있으면 `RESERVE_002`(올바르지 않은 예약 기간)로 거절한다. 지금 이 코드가 "재고 행이 없는 날이 낀 기간"에 쓰던 것과 같아서 외부 계약이 그대로다.
- 최대 숙박일은 14박이다. 15박부터 `RESERVE_002`로 거절한다. 박수만큼 점유 행을 한 트랜잭션에서 넣으므로 아주 긴 기간 한 번으로 행과 락을 오래 쥐는 것을 막는다. 경계 테스트는 14박 성공, 15박 거절이다.

### 5. 점유는 락처럼 쓰는 제약 장치이고, 예약 기록과 이력은 `reservation`이 맡는다
- `reservation`은 상태를 가진 예약 기록이고 영구히 둔다. `reservation_night`(`reservation_id`, `room_id`, `stay_date`, `price`)는 `(room_id, stay_date)` 유니크로 같은 객실 같은 날의 이중 예약을 DB가 막는 점유 장치이고 지금 점유 중인 것만 가진다.
- 생명주기

  | 사건 | 예약 상태 | 점유 행 |
  |---|---|---|
  | 예약 생성 | `PENDING_PAYMENT` | 날짜 오름차순으로 `INSERT`. 유니크 위반은 `RESERVE_003`(409) |
  | 결제 성공 | `CONFIRMED` | 그대로 |
  | 사용자 취소 | `CANCELED` | 삭제 |
  | 결제 시한 만료 | `EXPIRED` | 삭제 |
  | 이용 완료 | `COMPLETED` | 그대로(과거 날짜라 새 예약과 충돌하지 않는다). 쌓이면 오래된 행을 지우는 정리 배치를 나중에 둔다 |

- 취소·만료 행을 지우는 이유: MySQL에는 활성인 행만 유니크로 거는 부분 유니크가 없어서, 취소된 예약의 행이 남아 있으면 그 날짜를 다시 팔 수 없다. 삭제하면 취소가 곧 복구이고 `restoreStock` 같은 별도 복구 로직이 필요 없다.
- 취소는 예약·결제 상태 변경과 점유 행 삭제를 같은 트랜잭션에서 한다. 부분 환불(A1)에서 박별 가격이 필요하면 삭제하기 전에 읽는다. 만료는 상태를 `EXPIRED`로 바꾸는 것이 성공했을 때만 삭제한다(결제와 만료의 경쟁은 R5-4에서 조건부 `UPDATE`로 다룬다).
- 점유 행은 이력을 대신하지 않는다. 취소 사실과 시각, 기간, 총액은 `reservation`이, 결제와 환불 내역은 `payment`와 `payment_cancel_history`가 남긴다. 지금 비어 있는 것(만료 시각, 예약 쪽 사유, 상태 변화의 전체 순서)은 R2-4에서 예약 상태 이력(`reservation_status_history`)으로 채운다.

### 6. 락 정책
- 예약 생성의 객실 락(`LOCK:room:{roomId}`)은 점유 구조(사이클 3~4)를 먼저 커밋해 락이 켜진 상태로 전체 테스트가 통과함을 확인한 뒤, 같은 브랜치의 다음 커밋에서 제거했다. 구조 변경과 동시성 방식 변경을 한 사이클에 섞으면 테스트가 깨질 때 원인을 찾기 어렵다.
- 제거하기 직전 커밋에 태그(`study/room-distributed-lock`)를 달아 보존해서, 복습하거나 R4에서 그 버전으로 부하 측정을 할 수 있게 한다. 소스에는 죽은 코드를 남기지 않는다.
- 제거 커밋에서 함께 처리했다: 점유 `INSERT`의 유니크 위반을 `RESERVE_003`(409)으로 매핑한다(그대로 두면 500이다), 날짜 오름차순 `INSERT`로 데드락을 피한다, 데드락이 나면 재시도하거나 409로 처리한다.
- 결제(`payment:reservationId`), 취소(`reserveCancel:reservationId`), 숙소 상세·리뷰 캐시 락은 그대로 둔다. 결제와 취소는 PG라는 외부 호출이 끼어 DB 제약이 대신할 수 없고(멱등키가 생기는 R5-5에서 다시 본다), 캐시 락은 캐시가 비는 순간 몰리는 요청이 DB로 가지 않게 하는 목적이라 제약이나 Bulkhead로 대체할 수 없다.
- 폭주 보호(객실별 동시 처리 수 제한, 즉시 거절 `429`, 대기열)는 이 구조가 정해진 뒤 R4와 A5에서 다룬다. 평소 예약 API는 `201`/`409`/`429` 계약을 유지하고, 부하에 따라 같은 호출의 의미를 바꾸지 않는다.

### 7. 이번에 하지 않는 것
요금표와 차단일을 입력하는 관리자 기능, 운영자 취소, 고객 알림은 이 프로젝트의 범위 밖이거나 R2-5(취소·환불 정책)에서 정한다. 요금표와 차단일은 Fixture가 직접 저장한다.

## 검토한 대안
- 지금 구조 유지(날짜별 재고 행을 미리 채움): 가격과 가용성을 한 곳에서 다루지만 롤링 배치, 예약과 연결 없음, 락과 버전에 의존하는 정합성이 남는다.
- 재고 테이블 없이 겹치는 유효 예약으로 판단: 미리 채울 것이 없지만 MySQL에는 겹침 제약이 없어 객실 단위로 직렬화해야 하고 날짜별 가격은 별도 구조가 필요하다.
- 날짜별 재고 수량(카운터): 한 객실 종류에 호실이 여러 개일 때 맞는다. 호실 단위라 해당하지 않고 행을 미리 채우는 롤링도 그대로다.
- 차단일을 점유 테이블에 `type = BLOCK` 행으로 같이 두기: 유니크 하나로 예약과 차단을 막지만, 이미 예약된 날은 차단 행을 넣을 수 없어 예약 취소와 차단 사이에 다시 팔릴 수 있고 `reservation_id`가 `NULL`이 되어 의미가 섞인다.
- 취소·만료 점유 행을 지우지 않고 활성 여부로 표시: 계산 컬럼을 활성일 때만 값이 있게 하고 거기에 유니크를 거는 방법이 있지만 컬럼과 제약이 복잡하고, 이력은 `reservation`에 이미 있어서 얻는 것이 작다.
- 예약 테이블을 활성 전용으로 줄이고 종료된 예약을 히스토리 테이블로 이동: `payment`와 `review`가 `reservation_id`로 예약을 직접 참조해서 행을 옮기면 FK가 끊긴다.
- 요금을 기간 규칙(`start_date`, `end_date`, `price`)으로: 행은 줄지만 날짜가 어느 규칙에 속하는지 범위 비교가 필요해 복잡하다. 주말 요금처럼 반복 규칙이 필요해지면 요금 규칙 테이블을 따로 둔다.
- 가격을 SQL 집계 한 방(`base × 박수 + SUM(예외 − base)`)으로 계산: 쿼리 한 번에 끝나지만 날짜별 가격(스냅샷에 필요)을 줄 수 없고 자바 쪽에 별도 구현이 또 생겨 두 구현이 어긋날 수 있다.
- 예약 락을 유지하되 대기를 줄이거나 (객실, 날짜) 단위 락, Redis 사전 확인: R4에서 측정으로 비교할 후보다. 정합성은 제약이 맡으므로 락은 필수가 아니다.

## 결과
- 사이클 계획(로드맵 R2-1): 1) 이 ADR, 2) `room_special_price` 도입(가격 계산을 `Room.calculateStayPrice`로 모으고 `ROOM_INVENTORY.price` 제거), 3) `reservation_night` 도입(예약·취소·만료와 숙소 검색·객실 목록의 가용성 쿼리가 점유와 차단을 쓰도록), 4) `ROOM_INVENTORY` 제거(Fixture, 테스트, 샘플 데이터 정리), 5) 예약 락 제거(사이클 3·4와 같은 브랜치의 별도 커밋, 구현 완료). 각 사이클은 테스트를 먼저 고치고 전체 통과를 확인한 뒤 커밋하며, 엔티티가 바뀌면 같은 변경에서 `docs/erd.md`도 갱신한다.
- 외부 API의 응답과 에러 코드는 그대로여야 한다(가격 합산 결과, `RESERVE_002`, `RESERVE_003`, `RESERVE_004`). 기존 동시 예약, 재고 부족, 검색·목록 가격 테스트가 안전망이다. 바뀌는 것은 주로 Fixture와 데이터 준비(`createRoomWithInventories`, `createRoomInventoriesWithNightlyPrices` 등)다.
- 새 테이블 세 개(`reservation_night`, `room_special_price`, `room_blocked_date`)가 생기고 `room_inventory`가 없어진다. 테이블 수는 늘지만 행은 예약, 특별 요금, 차단일에만 생겨 객실×날짜로 미리 채우던 행이 사라진다.
- 재고 행이 없는 객실도 예약 가능해진다(판매 날짜를 행의 존재로 표현하던 방식이 사라짐). 막는 날은 `room_blocked_date`로만 표현한다.
- 구현 결과: 락 없이 점유 `INSERT`의 유니크 위반(`DataIntegrityViolationException`)과 교착(`ConcurrencyFailureException`)을 409 `RESERVE_003`으로 매핑했다. 사전 조회를 꺼도 동시 예약 테스트가 통과해 유니크 키가 경합의 최종 판정을 맡음을 확인했다(사전 조회는 빠른 실패와 에러 우선순위를 위해 남겼다).
- 가격 조회와 점유 `INSERT` 사이에 요금표가 바뀌는 좁은 틈이 있다. 같은 트랜잭션에서 조회와 `INSERT`를 하고 검증에 쓴 값을 그대로 `reservation_night.price`에 넣어 줄인다. 요금 변경이 드물어 허용한다.
- 지금 검색은 `room.isReservable`과 숙소의 운영 여부(`isOperational`)를 보지 않아 예약할 수 없는 객실이 검색에 나올 수 있다. 이번 구조 변경과 별개라서 바꾸지 않고 따로 확인한다.
- 락 제거 뒤 같은 객실에 요청이 폭주하면 같은 칸을 다투는 요청이 앞 트랜잭션이 끝날 때까지 DB 커넥션을 쥐고 대기하고, 앞 트랜잭션이 롤백되면 데드락이 날 수 있다. 이 한계의 측정과 보호 장치는 R4와 A5에서 다룬다.
