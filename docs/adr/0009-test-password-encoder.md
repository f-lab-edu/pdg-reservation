# 0009. 테스트의 비밀번호 인코더 강도

- 상태: 채택
- 날짜: 2026-11-01

## 맥락
- 거의 모든 통합 테스트가 회원 가입을 거치고, 로그인 테스트는 비밀번호 검증도 한다.
- 운영의 `BCryptPasswordEncoder`는 기본 강도 10이라 해시 한 번이 느리고, 테스트가 늘수록 시간이 쌓인다.

## 결정
- 테스트에서는 `BCryptPasswordEncoder`의 강도를 허용되는 최소값 4로 낮춘 `PasswordEncoder`를
  `@Primary` 테스트 빈으로 등록한다(`TestPasswordEncoderConfig`, `@IntegrationTest`가 가져온다).
- 알고리즘은 운영과 같은 BCrypt로 유지하고 강도만 낮춘다. 운영 코드는 바꾸지 않는다.

## 검토한 대안
- 강도 그대로: 가장 단순하지만 가입·로그인 테스트가 느려진다. 강도 10은 `encode`, `matches`가 각각 약 54ms다.
- `FakePasswordEncoder`(평문에 접두어를 붙이는 결정적 구현): 해시 시간이 0이고 단언이 단순해진다. 쓰지 않았다.
  - 실제 BCrypt에서만 드러나는 버그를 통과시킨다. 비밀번호를 `matches`가 아니라 해시 문자열 `equals`로 비교하는 코드(BCrypt는 매번 해시가 달라 실패하지만 Fake는 항상 같아 통과), 해시(60자)가 DB 컬럼 길이에 안 맞는 문제, 같은 비밀번호는 같은 해시라는 가정이 그렇다.
  - 가입 테스트가 "저장된 비밀번호가 해시되어 있다", 로그인 테스트가 "해시를 비교한다"는 실제 동작을 확인하는데, Fake로는 그 확인의 의미가 약해진다.
  - 테스트 가이드는 대역을 실제 구성요소를 구동하거나 제어할 수 없을 때(예: 외부 PG)에만 쓰게 한다. 인코더는 같은 JVM에서 제어할 수 있다.
  - 강도 4면 `encode`, `matches`가 각각 약 1ms라 대역으로 더 줄여도 이득이 작다.

## 결과
- 해시 1회가 강도 10에서 약 54ms, 4에서 약 1.1ms로 약 49배 빠르다. 회원 한 명 준비(가입+로그인)가 약 108ms에서 약 2.1ms로 준다(측정은 `docs/test-speed.md`).
- 강도가 낮아 해시 시간 특성은 운영과 다르다. 성능이나 보안 강도를 확인하는 테스트에는 쓸 수 없다.
- Spring 없이 엔티티·도메인 단위 테스트(테스트 가이드의 "엔티티 단위 테스트는 로직이 생긴 뒤")를 쓰게 되면, 그 테스트에서는 컨텍스트가 없어서 `new BCryptPasswordEncoder(4)`보다 `FakePasswordEncoder`가 간단한지 그때 다시 검토한다.
