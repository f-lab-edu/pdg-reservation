# 0011. 평점 갱신과 캐시 무효화 방식 (리뷰)

- 상태: 채택
- 날짜: 2026-11-05

## 맥락
- 리뷰를 쓰거나 지우면 Kafka 소비자(`ReviewKafkaConsumer`)가 비동기로 숙소 평점(합계, 개수, 평균)을 갱신하고 캐시를 무효화한다.
- 관련 캐시는 둘이다.
  - 리뷰 목록 첫 페이지: 숙소당 조건 조합(최소 평점 × 정렬 × 페이지 크기)만큼 키가 생긴다.
  - 숙소 상세: 숙소당 키가 하나(`숙소 id`)이고 평점을 담는다.
- 리뷰 테스트에서 평점을 확인하는 조회가 "기대 4.0, 실제 0.0"으로 간헐적으로 실패하면서 숙소 상세 캐시의 문제가 드러났다. 소비자는 28ms 만에 평점을 갱신했는데도 10초 동안 옛 값이 남았다. 원인은 두 가지였다.

### 이슈 1. 갱신 뒤 삭제 경쟁 (캐시 어사이드)
- 숙소 상세는 소비자가 평점을 갱신한 뒤 키를 지워서 무효화했다. 상세를 조회하는 요청이 DB에서 옛 평점을 읽은 뒤, 소비자가 평점을 갱신하고 키를 지우고 나서야 그 옛 값을 캐시에 넣으면, 지운 의미가 없어지고 옛 평점이 TTL 동안 남는다.
- 스파이로 순서를 강제한 테스트(`평점이 갱신되는 도중에 끝난 조회가 옛 평점을 캐시에 남기지 않는다`)로 항상 재현된다.

### 이슈 2. 커밋 전에 무효화한다
- 소비자의 `updateAccommodationRating`은 `@Transactional`이라 DB 갱신, 캐시 무효화(삭제 또는 세대 증가) 다음에 커밋된다. 무효화는 Redis에 즉시 반영되는데 DB 갱신은 아직 커밋 전이다.
- 그 사이에 들어온 조회는 새 키(또는 지워진 키)를 찾아 미스가 나고, 아직 커밋되지 않아 보이지 않는 옛 평점을 DB에서 읽어 새 키에 캐시한다. 세대 키로 바꿔도 이 문제는 남는다.
- 세대 증가가 일어나는 순간에 상세를 조회하게 하는 테스트(`평점 갱신이 커밋되기 전에 들어온 조회가 옛 평점을 새 세대의 캐시에 남기지 않는다`)로 항상 재현된다.

## 결정
- 리뷰 목록 캐시는 세대 키(Generation Key) 방식으로 무효화한다(원래 적용됨). 숙소별 세대 번호(`accommodation:generation:{숙소 id}`)를 캐시 키에 넣고, 소비자가 번호를 올리면 이후 조회는 새 키로 찾아 DB에서 새로 읽는다.
  - 이유: 키 조합이 방대해서 모두 찾아 지우기 어렵다(`KEYS`는 Redis를 멈추고, `SCAN`은 훑는 부하가 크고, 키 인덱스는 관리가 번거롭다). 번호만 올리면 지우는 작업이 없어 Redis 부하가 없고, 옛 키는 TTL로 사라진다.
- 숙소 상세 캐시도 같은 세대 키(Generation Key) 방식으로 바꾼다 (이슈 1). 늦게 들어온 옛 값이 이미 아무도 읽지 않는 옛 세대 키에 쌓인다. 세대 번호는 리뷰 목록과 숙소 상세가 함께 쓰는 숙소별 세대(`AccommodationCacheGenerationService`)이다. 소비자는 더 이상 상세 캐시를 지우지 않는다.
- 세대는 DB 트랜잭션이 커밋된 뒤에 올린다 (이슈 2). `TransactionSynchronization.afterCommit`에 등록한다. 세대가 오른 시점에는 새 평점이 이미 DB에 반영되어 있어서, 새 키로 조회한 요청은 새 평점을 읽는다. 롤백되면 세대도 오르지 않는다.
- 숙소 평균 평점은 갱신된 합계와 개수로 계산한다. MySQL의 `UPDATE`는 `SET`을 왼쪽부터 적용하고 앞에서 바꾼 값을 뒤의 식에서 쓴다. 갱신 전 값으로 계산하는 식이면 두 번째 리뷰부터 평균이 어긋난다(4.0, 2.0이면 3.0이 아니라 2.7).

- 용어: 이 방식은 Versioning이 아니라 Generation Key다. Versioning은 저장할 때 데이터의 버전(DB 버전 컬럼, 갱신 시각)을 비교해 오래된 값의 저장을 거부하는 방식이고, Generation Key는 키에 세대 번호를 넣고 번호를 올려 이전 세대의 캐시를 읽히지 않게 하는 방식이다. 우리는 저장할 때 비교하지 않으므로 후자다.

## 검토한 대안
- 갱신 뒤 키 삭제(원래의 숙소 상세): 단순하고 키가 하나일 때 흔한 방식이지만, 이슈 1의 경쟁이 있다.
- 짧은 TTL로 옛 값이 남는 시간을 줄이기: 경쟁은 그대로 남고 남는 시간만 줄어든다.
- 지연 이중 삭제(갱신 직후와 잠시 뒤 두 번 삭제): 경쟁을 줄이지만 완전히 없애지 못하고, 지연 시간을 정해야 한다.
- 평점을 상세 캐시에서 분리(본문은 길게 캐시, 평점은 매번 DB 조회): 코드 변경이 크고 상세 요청마다 DB 조회가 늘어난다.
- 갱신과 조회를 같은 락으로 묶기: 캐시 쓰기(`@Cacheable`)가 락 밖에서 일어나서 구조를 바꿔야 한다.
- 리뷰 목록의 `KEYS + DEL`, `SCAN + DEL`, 키 인덱스: 위 이유로 쓰지 않았다.
- 커밋 뒤 무효화를 스프링 이벤트(`@TransactionalEventListener(AFTER_COMMIT)`)로 하기: 이 프로젝트의 다른 이벤트와 일관되지만 이벤트 클래스와 리스너가 새로 필요하다. 같은 패턴이 하나뿐이라 `afterCommit` 한 군데로 충분하다고 보았다. 같은 패턴이 늘어나면 이벤트로 모은다.

## 결과
- 세대 키는 조회마다 세대를 읽는 Redis `GET`이 한 번 더 든다. 옛 세대 키는 TTL까지 남는다. 세대가 오르면 새 키는 비어 있어 첫 조회들이 DB를 읽는데, 락과 재확인(double-check)이 같은 DB 읽기가 몰리는 것을 줄인다.
- 갱신이 반영되는 시점은 소비자가 번호를 올린 뒤다(최종 일관성). 번호가 오르기 전에 시작한 요청은 옛 값을 한 번 받을 수 있지만 다른 요청에는 번지지 않는다.
- 커밋 뒤 단계에서 세대 증가가 실패하면(예: 그 순간 Redis 장애) 이미 커밋된 DB 갱신을 되돌릴 수 없고 멱등성 기록도 커밋되어 Kafka 재시도가 건너뛴다. 이때는 로그를 남기고, 옛 캐시는 TTL이 지나야 갱신된다. 커밋 전에 올리던 이전 방식은 Redis 오류가 트랜잭션을 롤백시켜 재시도되었으므로, 이 부분은 약해진 대신 이슈 2를 없앤 것이다.
- 리뷰 목록과 숙소 상세가 같은 세대를 쓰므로 소비자가 번호를 한 번 올리면 둘이 함께 무효화된다. 평점이 바뀌는 시점(리뷰 이벤트)과 두 캐시가 바뀌는 시점이 같기 때문이다. 숙소 정보 자체가 바뀌는 기능(관리자 기능)이 생기면 같은 번호를 올려야 한다.
- 세대는 처음에는 이름이 `review:version:`인 키였고, 숙소 기준 서비스로 옮기며 `accommodation:version:`, 이어서 `accommodation:generation:`(`AccommodationCacheGenerationService`)으로 바꿨다. 캐시 키의 `:v:`도 `:gen:`으로 바꿨다. 캐시라서 Redis에 남은 옛 키는 무시되고 번호는 1부터 다시 시작한다.
- 리뷰 삭제 이벤트가 생성 이벤트로 발행되던 문제(`REVIEW_DELETED`)는 별도로 수정했다.
